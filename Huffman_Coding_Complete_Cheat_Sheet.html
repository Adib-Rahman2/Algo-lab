1. Fundamentals

What Huffman coding is and why it is used

Huffman coding (David Huffman, 1952) builds an optimal prefix code: a binary codeword for every symbol so that the total number of bits needed for a message with known symbol frequencies is as small as possible. Frequent symbols get short codewords, rare symbols get long ones.

It is a greedy algorithm: repeatedly merge the two least frequent items. It is used inside real compression formats (DEFLATE in ZIP/gzip/PNG, JPEG, MP3), and the same merge procedure solves “optimal merge pattern” and “minimum cost to connect ropes”.

Core intuition The two rarest symbols should sit at the very bottom of the tree as siblings, because that is where long codes do the least damage. Glue them into one “super-symbol” whose frequency is their sum, and repeat the same reasoning on the smaller alphabet.

Why prefix codes matter

With a = 0, b = 01, c = 1 (not prefix-free), the bits “01” could mean b, or a followed by c. Decoding is ambiguous. With a = 0, b = 10, c = 11 (prefix-free) every bit string has one parse. Every symbol sits at a leaf, so a codeword can never be on the path to another one.

Kraft inequality (any prefix code): Σ 2−li ≤ 1. A full tree (every Huffman tree with ≥ 2 symbols) gives equality: Σ 2−li = 1.
Shannon bound for the Huffman average length L: H ≤ L < H + 1.

When to use it and when not to

Use Huffman when
  • You know (or can count) the frequency of each symbol and want minimum total bits.
  • You must repeatedly combine two items where combining costs their sum and you want the minimum total cost (files, ropes, sorted lists).
  • The question says “optimal prefix code”, “variable-length code”, “minimum weighted path length”, “expected number of yes/no questions”.
Do not use Huffman (or use with care) when
  • Symbols must keep alphabetical order in the tree (that is the Hu–Tucker problem / optimal alphabetic tree; also different from optimal BST).
  • The cost of combining is not the sum, or you can only merge adjacent items (that is an interval DP, e.g. stone merging).
  • Codeword length has a hard maximum (length-limited Huffman, package-merge).
  • All frequencies are equal and n is a power of 2: Huffman gives the same as fixed-length (no gain).
  • Data has long repeats or patterns (LZ77/LZW or RLE exploit those; Huffman only uses single-symbol frequencies).

2. The greedy algorithm, its correctness and complexity

Pseudocode (CLRS HUFFMAN)

HUFFMAN(C)
  n ← |C|
  Q ← min-priority queue of C keyed on f
  for i ← 1 to n − 1
      allocate a new node z
      z.left  ← x ← EXTRACT-MIN(Q)
      z.right ← y ← EXTRACT-MIN(Q)
      z.freq  ← x.freq + y.freq
      INSERT(Q, z)
  return EXTRACT-MIN(Q)          ▷ the root

ASSIGN-CODES(node, path)
  if node is a leaf: code[node.symbol] ← path   (use "0" if path is empty)
  else ASSIGN-CODES(node.left,  path + "0")
       ASSIGN-CODES(node.right, path + "1")
Conventions used on this whole sheet (state them in exams)
  1. The first extracted node (smaller) becomes the left child; left edge = 0, right edge = 1.
  2. Ties between equal weights: the node that has been in the queue longer goes first (leaves in the order given, then merged nodes in creation order). For text, leaves are ordered by character.
Other books put the larger node on the left or label edges the other way. The codewords change, but code lengths and the total cost do not. Any consistent convention is accepted if you state it.

Two ways to compute the cost

B(T) = Σleaves f(c)·dT(c) = Σinternal nodes z f(z)

Why the second form works: a leaf at depth d has d ancestors, and its frequency is included in each ancestor’s weight exactly once. So summing all merged weights counts every frequency d times. Use this as a quick check: in the CLRS example the merged weights are 14 + 25 + 30 + 55 + 100 = 224, which equals the leaf-by-leaf sum.

Correctness proof (greedy choice + optimal substructure)

Lemma 1 (greedy choice). Let x, y be the two symbols with the lowest frequencies. Some optimal prefix code has x and y as sibling leaves at maximum depth (so their codewords have the same length and differ only in the last bit).

Proof of Lemma 1 (exchange argument)

Take any optimal tree T. Because it is full, the deepest level contains two sibling leaves a, b; assume f(a) ≤ f(b) and f(x) ≤ f(y). Then f(x) ≤ f(a), f(y) ≤ f(b), and d(a) ≥ d(x), d(b) ≥ d(y).

Swap x with a to get T′. The change in cost is

B(T) − B(T′) = (f(a) − f(x))(dT(a) − dT(x)) ≥ 0

since both factors are non-negative. So T′ is no worse. Swapping y with b similarly gives T″ with B(T″) ≤ B(T). T was optimal, so T″ is optimal too, and in T″ the leaves x, y are deepest siblings.

Lemma 2 (optimal substructure). Replace x, y by a new symbol z with f(z) = f(x) + f(y), giving alphabet C′. If T′ is optimal for C′, then replacing leaf z in T′ by an internal node with children x, y gives an optimal tree T for C.

Proof of Lemma 2

Depths of all other leaves are unchanged and dT(x) = dT(y) = dT′(z) + 1, so

B(T) = B(T′) + f(x) + f(y)

Suppose some tree T* for C had B(T*) < B(T). By Lemma 1 we may assume x, y are siblings in T*. Merging them into z gives T*′ for C′ with B(T*′) = B(T*) − f(x) − f(y) < B(T) − f(x) − f(y) = B(T′), contradicting optimality of T′.

Theorem. By induction on n: each greedy merge is safe (Lemma 1) and leaves a smaller instance of the same problem (Lemma 2), so HUFFMAN produces an optimal prefix code.

4. Converting story problems into Huffman problems

Huffman questions are often disguised as compression, communication, file-merging or questioning games. Use this routine.

  1. Find the items and their weights. Symbols with counts, percentages or probabilities; or files/ropes/lists with sizes.
  2. Check the cost structure. Is the cost of an item proportional to “frequency × depth / number of bits / number of times it is touched”? Or is “combining two things costs their sum”? Both mean Huffman.
  3. Check freedom of order. Huffman may combine any two items. If only adjacent items can be combined, or the leaves must stay in alphabetical order, it is a different problem.
  4. Identify the output. Codewords? Tree? Total bits? Average length? Savings vs fixed length? Decoded message? Minimum merge cost?
  5. Write the mapping (“symbols = …, weights = …, required = B(T) / codes / …”) and run the standard merges.

Worked translations

A. Direct frequency table

“Construct a Huffman code for a:45, b:13, c:12, d:16, e:9, f:5.” Already in standard form. Answer: Dry run 1.

B. Compress a message (count characters first)

“A telegraph operator must send ‘MISSISSIPPI’. Design the shortest binary code where no codeword starts another codeword, and give the number of bits sent.”

Extract: “no codeword starts another” = prefix code; “shortest” = Huffman. Count: I 4, M 1, P 2, S 4. Answer: S = 0, I = 11, M = 100, P = 101; 21 bits (vs 22 with a 2-bit fixed code, 88 with ASCII). See Dry run 4.

C. Percentages from a survey or sensor

“A weather station sends one of five states: Sunny 40%, Cloudy 20%, Rain 20%, Fog 10%, Snow 10%. Design a binary code minimising the expected bits per report.”

Extract: weights = probabilities; output = codes + expected length. Map Sunny=A … Snow=E: ABL = 2.2 bits per report (Dry run 3), versus 3 bits fixed. Entropy 2.12 bits.

TipPercentages can be used as integers (40, 20, 20, 10, 10) for easier arithmetic: the tree is the same; divide the cost by 100 at the end.

“A secret item is chosen with known probabilities. You may ask yes/no questions of the form ‘is it in set S?’. Design a questioning strategy minimising the expected number of questions.”

Each strategy is a binary tree (yes = 1, no = 0); the expected number of questions = Σ p·depth. That is exactly Huffman. With the probabilities of story C, the minimum expected number of questions is 2.2.

Standard variations

V1. Build the tree and codes from a frequency table “construct a Huffman code”
Looks like
“Construct the Huffman tree and codewords for a:45, b:13, …”
Recognise
Symbols with frequencies/probabilities + “Huffman”, “optimal prefix code”, “variable-length code”.
Input
n pairs (symbol, frequency).
Output
Tree, a codeword per symbol, usually total bits.
Approach
Min-heap; n − 1 times extract two minima, make parent, insert; DFS for codes.
Steps
Sort/heapify → merge table → draw tree bottom-up → label 0/1 → read codes → compute Σ f·l.
Complexity
O(n log n) time, O(n) space.
Edge cases
n = 1 (code “0”); ties (state rule); large frequencies (use long long).

The implementation stores nodes in a vector and keeps (frequency, index) pairs in the heap. Because an index grows with creation time, ties are broken “older node first” automatically, with no custom comparator and no pointers to free.

h01_huffman.cpp
#include <bits/stdc++.h>
using namespace std;

struct Node {
    long long freq;
    string sym;
    int left = -1, right = -1;
};

vector<Node> pool;
map<string, string> code;

void assign(int u, const string &path) {
    if (pool[u].left == -1) { code[pool[u].sym] = path.empty() ? "0" : path; return; }
    assign(pool[u].left, path + "0");

V7. Is this code prefix-free? (and Kraft sum) “is the code uniquely decodable?”
Looks like
“Which of these codes are prefix codes: {0, 10, 110, 111}, {0, 01, 11}?”
Approach
Sort codewords lexicographically; if any codeword is a prefix of another, it is a prefix of its sorted successor. Kraft sum Σ 2−l ≤ 1 is necessary; = 1 for a full tree.
Steps
{0, 10, 110, 111}: sorted, no neighbour prefix → prefix-free; Kraft = ½ + ¼ + ⅛ + ⅛ = 1. {0, 01, 11}: “0” prefixes “01” → not prefix-free (Kraft is 1, which shows Kraft alone does not prove prefix-freeness).
Complexity
O(n log n · ℓ) for sorting strings of length ≤ ℓ.
Edge cases
Duplicate codewords are prefixes of each other. A Kraft sum < 1 means some branch is unused: the code is prefix-free but cannot be optimal.

V11. k-ary (ternary) Huffman code “code alphabet {0, 1, 2}”
Looks like
“Construct an optimal ternary prefix code for a:45, b:13, c:12, d:16, e:9, f:5” (a classic textbook exercise).
Recognise
Codewords use k symbols (digits 0..k−1), or k items are combined at a time.
Approach
Add dummy symbols of frequency 0 until (n + dummies − 1) mod (k − 1) = 0, so every merge takes exactly k nodes and the tree is full. Then repeatedly merge the k smallest.
Steps
n = 6, k = 3: (6 − 1) mod 2 = 1 → add 1 dummy. Merges: {0, 5, 9} → 14; {12, 13, 14} → 39; {16, 39, 45} → 100. Codes: d = 0, c = 10, b = 11, f = 121, e = 122, a = 2. Cost = 153 ternary digits.
Complexity

Edge cases

A1. O(n) Huffman for sorted frequencies (two queues) Advanced

If leaves are already sorted, merged weights come out in non-decreasing order, so a plain FIFO queue keeps them sorted. Keep queue 1 = leaves, queue 2 = merged nodes; the minimum is always at one of the two fronts. O(n) after sorting (van Leeuwen, 1976).

h08_two_queue.cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    int n;
    cin >> n;
    vector<long long> f(n);
    for (auto &x : f) cin >> x;
    sort(f.begin(), f.end());
    queue<long long> leaves, internal;
    for (long long x : f) leaves.push(x);
    auto takeMin = [&]() {
        long long v;
        if (internal.empty() || (!leaves.empty() && leaves.front() <= internal.front())) {
            v = leaves.front(); leaves.pop();
        } else {
            v = internal.front(); internal.pop();
        }
        return v;
    };
    long long cost = 0;
    while (leaves.size() + internal.size() > 1) {
        long long a = takeMin(), b = takeMin();
        cost += a + b;
        internal.push(a + b);
    }
    cout << "Huffman cost (sum of merges): " << cost << "\n";
}

A3. Adaptive (dynamic) Huffman Beyond typical syllabus

One pass: encoder and decoder start with the same empty tree (an NYT “not yet transmitted” node), update counts after every symbol and restructure the tree to keep the sibling property (FGK and Vitter algorithms). No frequency table has to be sent.

A4. Length-limited Huffman Beyond typical syllabus

When no codeword may exceed L bits (hardware tables), plain Huffman may violate the limit (Fibonacci case). The package-merge algorithm finds the optimal code under the limit in O(nL).

A5. Storing / sending the tree Advanced

Pre-order traversal: write 0 for an internal node and 1 followed by the 8-bit symbol for a leaf. The receiver rebuilds the tree recursively. Cost ≈ (2n − 1) + 8n bits, which is why Huffman does not pay off for very short messages. Canonical codes (A2) send only lengths.

    }
    while (pq.size() > 1) {
        Node *x = pq.top(); pq.pop();
        Node *y = pq.top(); pq.pop();
        pq.push(new Node('$', x->freq + y->freq, x, y));
    }
    printCodes(pq.top(), "");
}
Note on this version priority_queue is a max-heap, so the comparator returns a->freq > b->freq to make it a min-heap. With ties it does not guarantee a particular order, so codewords may differ from a hand trace even though lengths and total cost are optimal. The pool-and-index version (h01) is deterministic. Using '$' as an internal marker breaks if '$' is a real symbol; test for “no children” instead, as done above.

8. Exam question bank with solutions

Try each before opening the solution. All numeric answers were checked by program; codewords follow this sheet’s conventions (smaller/older left, left = 0).

Level 1: Basic

Q1. A file has 100 000 characters from 6 symbols. How many bits does a fixed-length code need?

⌈log2 6⌉ = 3 bits per symbol → 300 000 bits.

Q2. Build the Huffman code for a:10, e:15, i:12, o:3, u:4, s:13, t:1. Find the total bits.

Merges: t1+o3 = 4; u4+4 = 8; 8+a10 = 18; i12+s13 = 25; e15+18 = 33; 25+33 = 58. Codes: i = 00, s = 01, e = 10, a = 111, u = 1100, t = 11010, o = 11011. Total = 4+8+18+25+33+58 = 146 bits (fixed 3-bit: 174).

Q3. Is {00, 01, 10, 110, 111} a prefix code? What is its Kraft sum?

Yes (no codeword begins another). Kraft = 3·¼ + 2·⅛ = 1, so it is a complete (full-tree) code.

Q4. With a = 0, b = 101, c = 100, d = 111, e = 1101, f = 1100, decode 1100 0 100 1101 (spaces added for you).

f a c e → face.

Q5. How many internal nodes and total nodes does a Huffman tree for n ≥ 2 symbols have?

n − 1 internal nodes (one per merge), 2n − 1 nodes in total.

Q6. Ropes of lengths 1, 2, 3, 4, 5: minimum cost to join them all?

1+2 = 3; 3+3 = 6; 4+5 = 9; 6+9 = 15. Total 3 + 6 + 9 + 15 = 33.

Q7. What is the time complexity of Huffman’s algorithm and why?

O(n log n): n − 1 iterations, each with two EXTRACT-MIN and one INSERT on a binary heap of size ≤ n, each O(log n). Building the initial heap is O(n).

Q9. Probabilities 0.25, 0.25, 0.20, 0.15, 0.15 (A–E). Find the code, the average length, entropy and efficiency.

Merges (×100): D15+E15 = 30; C20+A25 = 45; B25+30 = 55; 45+55 = 100. Codes: C = 00, A = 01, B = 10, D = 110, E = 111. L = 0.25·2 + 0.25·2 + 0.2·2 + 0.15·3 + 0.15·3 = 2.30. H ≈ 2.2855. Efficiency ≈ 99.4%.

Q10. Show the queue contents after every iteration for frequencies 2, 3, 4, 5, 6 (A–E).

Start: A2, B3, C4, D5, E6. After 1: C4, D5, (5), E6 — note D5 (older) before the new 5. After 2: (5), E6, (9). After 3: (9), (11). After 4: (20). Codes: C = 00, D = 01, E = 11, A = 100, B = 101. Cost 5 + 9 + 11 + 20 = 45.

Q11. Give two different Huffman trees for frequencies 1, 1, 2, 2 and show both are optimal.

Tree 1 (older first): all lengths 2 → 2·(1+1+2+2) = 12. Tree 2 (newer first): 2 + 2 + 2 + 4 → lengths 1, 2, 3, 3 for weights 2, 2, 1, 1 → 2·1 + 2·2 + 1·3 + 1·3 = 12. Same cost, different shapes.

Q12. Frequencies a 45, b 13, c 12, d 16, e 9, f 5. A student uses a = 00 and the others 3 bits. Is it optimal?

Cost = 90 + 3·55 = 255 > 224 (Huffman). Kraft sum = ¼ + 5·⅛ = 0.875 < 1: a branch is wasted, so it cannot be optimal.

Q13. Could x = 0, y = 10, z = 11 be an optimal code for frequencies x 1, y 2, z 3?

No. The most frequent symbol (z) must not have a longer code than a less frequent one (x). Cost = 1 + 4 + 6 = 11; Huffman gives z = 0, x = 10, y = 11 → 3 + 2 + 4 = 9.

Q14. Six symbols with equal frequency 10. Is Huffman better than fixed length?

Yes, slightly: lengths 3, 3, 3, 3, 2, 2 → 160 bits vs 6 × 10 × 3 = 180. Equal frequencies give no gain only when n is a power of 2.

Level 3: Advanced

Q15. Story: a weather station sends Sunny 40%, Cloudy 20%, Rain 20%, Fog 10%, Snow 10% once per minute. How many bits per day with Huffman vs fixed length?

L = 2.2 bits/report; 1440 reports/day → 3168 bits vs 1440 × 3 = 4320 bits (26.7% less).

Q16. Optimal merge pattern: files of 20, 30, 10, 5, 30 records. Give the merge order and cost.

(5,10)→15, (15,20)→35, (30,30)→60, (35,60)→95. Cost 205.

Q17. Ternary Huffman for A 5, B 10, C 15, D 20, E 25, F 10, G 15.

n = 7, (7 − 1) mod 2 = 0 → no dummies. Merge {A5, B10, F10} → 25; {C15, G15, D20} → 50; {E25, 25, 50} → 100. Codes: E = 0, A = 10, B = 11, F = 12, C = 20, G = 21, D = 22. Cost = 175 ternary digits (binary Huffman: 270 bits).

Q18. Prove that in an optimal prefix code, if f(a) > f(b) then d(a) ≤ d(b).

If d(a) > d(b), swap a and b. Cost changes by (f(a) − f(b))(d(b) − d(a)) < 0, strictly cheaper: contradiction with optimality.

Q19. Prove that the Huffman tree is always full.

Every node created by the algorithm gets exactly two children. More generally, in an optimal tree a node with one child can be replaced by that child, reducing every depth below it by 1 and strictly reducing the cost (if any frequency is positive).

Q20. Show that lengths {1, 2, 2, 3} cannot be a prefix code.

Kraft sum = ½ + ¼ + ¼ + ⅛ = 1.125 > 1, violating Kraft’s inequality.

Q21. For frequencies equal to the first n Fibonacci numbers, what is the Huffman tree?

A spine: the sum of the first k Fibonacci numbers is Fk+2 − 1 < Fk+2, so the merged node always merges with the next leaf. Codes: the most frequent gets 0, next 10, …, last two get 1…10 and 1…11, length n − 1.

Q22. Show that the CLRS code satisfies H ≤ L < H + 1.

H ≈ 2.2199, L = 2.24: 2.2199 ≤ 2.24 < 3.2199 ✓. Efficiency ≈ 99.1%.

Q23. Programming: read n numbers and print the minimum cost of merging them (sum of merges).

Program h04 (V9). Use long long; n = 1 → 0.

Q24. Programming: read a line, print Huffman codes for each character (space included), the encoded string, and verify decoding.

Program h02 (V2). Test with “this is an example of a huffman tree” → 135 bits.

Q25. Why does Shannon–Fano not always give an optimal code?

It splits the sorted list top-down into two halves of nearly equal total probability. That split is a local decision at the top of the tree that cannot be undone, and for some distributions (for example 0.35, 0.17, 0.17, 0.16, 0.15) it produces a larger average length than Huffman’s bottom-up merging.

Q26. Huffman coding is greedy. Name the two properties that justify it and the problem it generalises.

Greedy-choice property (Lemma 1) and optimal substructure (Lemma 2). It solves minimum weighted external path length, so the same algorithm solves optimal merge pattern and connect-ropes.

11. Quick revision sheet

Core formulas
B(T) = Σ f(c)·d(c) = Σ internal weights
L = B(T)/Σf = Σ p·l
H = −Σ p log2 p,  H ≤ L < H + 1
Kraft: Σ 2−l ≤ 1 (= 1 for Huffman)
Fixed length ⌈log2 n⌉ bits
Algorithm Put all symbols in a min-heap. Repeat n − 1 times: x = min, y = min, z = x + y with left x, right y, insert z. Root = last node. Codes: DFS, left 0, right 1.
Complexity O(n log n) time, O(n) space; O(n) if frequencies are sorted (two queues); encode O(output bits); decode O(N).
Tree facts Full binary tree, n leaves, n − 1 internal, 2n − 1 nodes. Two rarest are deepest siblings. Max depth n − 1. More frequent → not longer code.
Key observations
  • Huffman is greedy; proof = exchange argument (greedy choice) + B(T) = B(T′) + f(x) + f(y) (optimal substructure).
  • Ties give different trees with the same cost; minimum variance takes older nodes first.
  • Merge-cost problems (files, ropes) are Huffman without codes.
  • k-ary: add zero dummies until (n − 1) mod (k − 1) = 0.
  • Equal frequencies with n = 2k give no saving.
Recognition keywords optimal prefix code · variable-length code · minimum bits · expected code length · entropy · merge files two at a time · connect ropes · yes/no questions · ternary code · decode the bits.

Standard template to write from memory

huffman_template.cpp
#include <bits/stdc++.h>
using namespace std;

struct Node { long long f; char c; int l = -1, r = -1; };
vector<Node> t;
map<char, string> code;

void dfs(int u, string p) {
    if (t[u].l == -1) { code[t[u].c] = p.empty() ? "0" : p; return; }
    dfs(t[u].l, p + "0");
    dfs(t[u].r, p + "1");
}

int main() {
    int n;
    cin >> n;
    priority_queue<pair<long long, int>, vector<pair<long long, int>>, greater<>> pq;
    for (int i = 0; i < n; i++) {
        char c; long long f;
        cin >> c >> f;
        t.push_back({f, c});
        pq.push({f, i});
    }
    while (pq.size() > 1) {
        int x = pq.top().second; pq.pop();
        int y = pq.top().second; pq.pop();
        t.push_back({t[x].f + t[y].f, 0, x, y});
        pq.push({t.back().f, (int)t.size() - 1});
    }
    dfs(pq.top().second, "");
    long long bits = 0;
    for (int i = 0; i < n; i++) {
        cout << t[i].c << " " << code[t[i].c] << "\n";
        bits += t[i].f * code[t[i].c].size();
    }
    cout << "Total bits: " << bits << "\n";
}
Last-minute exam tips
  1. Write the symbols sorted by frequency first, and check that the frequencies add up to the message length.
  2. State the conventions: smaller node left, left edge = 0, tie rule.
  3. Show a merge table (x, y, new node, queue) and the final tree. Draw merged nodes as circles with their sum.
  4. Read codes from root to leaf; check the most frequent symbol has the shortest code.
  5. Compute the cost two ways (Σ f·l and Σ merges) and make sure they agree.
  6. Compare with fixed-length (⌈log2 n⌉ bits) and ASCII (8 bits) if a saving is asked.
  7. For probabilities: give L, H, efficiency = H/L with 3–4 decimals.
  8. In the lab: test the CLRS table (224), “AAAA” (single symbol), and equal frequencies.
